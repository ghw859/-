## 一、项目架构与技术栈

### 1.1 系统架构

灵枢采用三端分离架构，通过 Vite 开发代理统一前缀 `/api` 路由到不同后端服务：

```
┌─────────────────────────────────────────────────────────┐
│                    前端 (Vue3 + Vite :5173)               │
│  路由代理：/api/ai/* → :8000，其余 /api/* → :8080        │
│  页面：预约 / 预填单 / 直通码 / 审计存证 / AI助手 / 看板  │
└──────────┬──────────────────────────┬──────────────────┘
           │                          │
           ▼                          ▼
┌──────────────────────┐    ┌──────────────────────────────┐
│  Java 后端 (:8080)    │    │  Python AI 服务 (:8000)       │
│  Spring Boot 3.2      │    │  FastAPI + Uvicorn             │
│  - 认证/预约/排队     │    │  - 材料预检（规则引擎）         │
│  - 直通码签发/凭证    │    │  - 数字人对话（规则+LLM双路径）  │
│  - 审计哈希链         │    │  - 网点热力图预测               │
│  - 网点/数据总览      │    │  - 预填单自然语言解析           │
│  - 信用分/文件上传    │    │  - 用户健康诊断                │
│  RestTemplate → AI   │    │  Redis 缓存 + 通义千问 LLM     │
└───────┬──────────────┘    └───────────────┬──────────────┘
        │                                   │
        ▼                                   ▼
┌──────────────────────┐    ┌──────────────────────────────┐
│  MySQL 8.0           │    │  Redis 7                     │
│  (业务数据/审计链)    │    │  (对话历史/热力图缓存/排队)   │
└──────────────────────┘    └──────────────────────────────┘
```

### 1.2 技术栈总览

| 层 | 技术选型 | 说明 |
|----|---------|------|
| 前端 | Vue 3.5 + TypeScript + Vite 8 | 组合式 API，Pinia 状态管理 |

## 二、AI 技术在项目中的具体介入环节与核心价值

### 2.1 AI 介入环节全景

灵枢在**六个核心业务环节**引入 AI 技术，覆盖用户从"咨询→准备→预约→办理→存证→回顾"的完整金融业务链路：

| 环节 | AI 能力 | 触发位置 | 技术路径 |
|------|---------|---------|---------|
| ① 智能导诊 | 数字人对话（意图识别+知识库+LLM） | AI 助手页 / WS | 规则引擎优先 → 通义千问 LLM 兜底增强 |
| ② 材料预检 | 业务材料完整性校验 | 直通码生成 `POST /api/qrcode/generate` | 纯规则引擎（Python `precheck_engine`） |
| ③ 网点推荐 | 实时客流预测+推荐 | AI 导航组件 / 预约页 | 基于历史客流的线性回归预测 |
| ④ 热力图预测 | 网点×时段负载预测 | 热力图 API | 线性回归+确定性扰动算法 |
| ⑤ 预填单解析 | 自然语言→结构化表单 | 预填单创建 | 正则提取+中文数字转换+关键词业务推断 |
| ⑥ 健康诊断 | 用户画像分析+建议生成 | 诊断 API | 确定性画像合成 → LLM 生成自然语言诊断 |

### 2.2 各环节技术实现详解

#### 环节①：数字人对话（`/api/ai/chat` + `/api/ai/chat/ws`）

**技术实现**（[chat_engine.py](file:///d:/MyProject/-/lingmou_ai/services/chat_engine.py)）：
- **规则层**：17+ 条知识库规则 `KB_RULES`，按优先级用正则匹配意图（网点推荐/排队查询/业务指导/转账/开户/存款/理财等），命中则返回对应话术
- **LLM 增强层**：规则未命中时，调用通义千问（qwen-turbo）生成回复；LLM 不可用时降级为 `rule_fallback`
- **多轮上下文**：Redis 按 `chat:{sessionId}` 存储对话历史（JSON 数组，最大限轮数+TTL）
- **情感识别**：标注 positive/neutral/negative

**核心价值**：7×24 智能大堂经理，替代实体网点排队咨询，降低人力成本；规则优先保证响应速度（<100ms）和金融话术合规性，LLM 兜底保证覆盖面。

#### 环节②：材料预检（`/api/ai/precheck` → `POST /api/qrcode/generate`）

**技术实现**（[precheck_engine.py](file:///d:/MyProject/-/lingmou_ai/services/precheck_engine.py) + [PrecheckBizSupport.java](file:///d:/MyProject/-/lingmou_backend/src/main/java/com/icbc/lingmou/service/support/PrecheckBizSupport.java)）：
- **业务枚举归一化**：前端 5 类业务枚举（cash_reserve/open_card/corp_transfer/cash_deposit/fx_exchange）→ Python 统一大写枚举
- **材料字段映射**：如 corp_transfer 的 recvName/recvCard 映射为 payeeName/payeeAccount
- **必填项校验**：按 `BUSINESS_MATERIALS` 配置表逐项校验，空串/0/null 判为缺失
- **返回契约**：`passed/missing/required/checked` + 中文缺失标签

**核心价值**：用户到达网点前**提前发现材料缺失**，避免"排到窗口才发现证件没带"的体验断裂。规则引擎保证 100% 可解释（不依赖模型黑盒），响应 <50ms。

#### 环节③：网点推荐（AI 导航组件 + 热力图）

**技术实现**（[heatmap_engine.py](file:///d:/MyProject/-/lingmou_ai/services/heatmap_engine.py)）：
- **预测算法**：合成历史客流 → 线性回归预测当日各时段负载 → 与 `busy/moderate/free` 状态基线融合 → 确定性扰动输出 10-100 负载百分比
- **缓存**：Redis 按 `heatmap:v2:{date}` 缓存热力图数据
- **前端消费**：AI 导航组件根据用户业务类型匹配最优网点，计算预计办理时长

**核心价值**：基于历史数据的智能分流，减少用户等待时间 15%-55%（诊断画像数据佐证），降低网点峰值压力。

#### 环节④：预填单自然语言解析（`/api/ai/parse-preform`）

**技术实现**（[preform_parser.py](file:///d:/MyProject/-/lingmou_ai/services/preform_parser.py)）：
- **字段提取**：正则匹配姓名、身份证号、手机号、金额（含中文数字转换如"五万"→50000）、地址、银行卡号
- **业务类型推断**：基于关键词（转账/开户/存款/外汇等）推断业务枚举
- **置信度计算**：综合提取字段数与匹配强度，低于阈值返回 `code=40001`

**核心价值**：用户用自然语言描述业务需求（如"向北京灵枢科技有限公司转账5万元"），AI 自动提取并结构化，减少手动填表 80% 操作量。

#### 环节⑤：用户健康诊断（`/api/ai/diagnosis`）

**技术实现**（[diagnosis_engine.py](file:///d:/MyProject/-/lingmou_ai/services/diagnosis_engine.py)）：
- **画像合成**：以 userId 为种子确定性生成预约数、办结率、信用分、高频业务、安全事件等 12 维画像
- **LLM 诊断**：画像数据 → 结构化 prompt → 通义千问生成 150-250 字中文诊断建议
- **规则兜底**：LLM 不可用时，按画像维度模板化拼接诊断文案

**核心价值**：主动发现用户金融健康风险（如信用分偏低、夜间大额交易风控），提供个性化建议。

### 2.3 关键问题解决与不可替代性

| 问题 | 传统方案痛点 | AI 方案解决 | 不可替代性 |
|------|-------------|-----------|-----------|
| 业务咨询排队 | 柜面人力有限，高峰期等待 30min+ | 数字人 7×24 即时响应，规则 <100ms | LLM 覆盖长尾问题，规则保证合规话术 |
| 材料缺失 | 到窗口才发现，二次跑腿 | 预约前 AI 预检拦截，提前补齐 | 规则引擎 100% 可解释，金融场景必须确定性 |
| 网点拥堵 | 凭经验选网点，撞峰 | 历史客流预测+智能分流 | 线性回归利用历史数据，人工无法实时计算 |
| 表单繁琐 | 手动填 10+ 字段 | 自然语言一键提取 | 正则+关键词推断比纯 LLM 更快更可控 |
| 金融健康盲区 | 无主动诊断 | 画像分析+LLM 生成个性化建议 | 多维数据综合分析，人工客服无法规模化 |
| 存证可信度 | 传统日志可篡改 | SHA-256 哈希链，逐条自洽 | 区块链思想保证审计不可篡改、可追溯 |

## 三、数据来源合法性说明

### 3.1 数据采集方式

| 数据类别 | 采集方式 | 具体内容 | 存储位置 |
|---------|---------|---------|---------|
| 用户注册信息 | 用户主动填写 | 用户名、密码（BCrypt 加密）、真实姓名、手机号、身份证号 | MySQL `users` 表 |
| 预约信息 | 用户预约时提交 | 网点 ID、业务类型、预约日期、时段 | MySQL `appointments` 表 |
| 预填单数据 | 用户自然语言输入 | 原始文本、AI 解析结果、图片 URL、签名 URL | MySQL `pre_forms` 表 |
| 直通码材料 | 直通码生成时提交 | 姓名、身份证、手机、金额、收款方信息等 | MySQL `vouchers` 表 + `audit_logs` 审计链 |
| 对话历史 | 用户与 AI 对话 | sessionId、消息内容（Redis，TTL 过期自动清除） | Redis `chat:{sessionId}` |
| 热力图数据 | 基于历史客流合成 | 预测的网点×时段负载百分比 | Redis `heatmap:v2:{date}` |
| 诊断画像 | 基于 userId 确定性生成 | 预约数、信用分、高频业务等（非真实用户行为数据） | 内存计算，不持久化 |

**重要说明**：
- **无网络爬取**：项目不采集任何外部互联网数据
- **无第三方数据源**：除通义千问 LLM API 调用（仅传输用户输入的对话文本）外，不向任何第三方共享用户数据
- **无被动监听**：所有数据均由用户主动提交或基于用户 ID 确定性合成

### 3.2 授权范围

| 数据使用目的 | 授权依据 | 数据范围 |
|-------------|---------|---------|
| 用户认证与服务提供 | 用户注册时同意 | 注册信息 + 预约 + 预填单 |
| AI 对话响应 | 用户主动发起对话 | 当前会话消息（Redis，TTL 自动过期） |
| 材料预检 | 用户发起直通码生成 | 提交的业务材料字段（仅当次调用） |
| LLM 生成诊断 | 用户查看诊断 | userId + 合成画像（不含真实身份证/手机号） |
| 审计存证 | 直通码签发时自动触发 | 凭证号、业务类型、脱敏身份信息 |
| 通义千问 LLM 调用 | DashScope API 服务条款 | 仅对话文本和画像摘要，不传输身份证号/手机号 |

**LLM 调用数据边界**：
- 传给通义千问的数据：对话文本、诊断 prompt（含预约数/信用分/业务类型等画像摘要）
- **不传输**：身份证号、手机号、银行卡号、密码等敏感 PII

### 3.3 隐私保护措施

| 保护措施 | 实现方式 | 涉及代码 |
|---------|---------|---------|
| 密码加密 | BCrypt 哈希存储，不明文 | 后端 `RegisterRequest` → `UserService` |
| JWT 认证 | Token 不含敏感信息，仅 userId/username/role | `JwtUtils` + `AuthInterceptor` |
| 用户隔离 | 所有"我的 xx"接口按 token 中的 userId 强制隔离 | `httpRequest.getAttribute("userId")` |
| PII 脱敏（审计） | 身份证：前4+********+后4；手机号：前3+****+后4 | [AuditLogServiceImpl.toCustomerResponse()](file:///d:/MyProject/-/lingmou_backend/src/main/java/com/icbc/lingmou/service/impl/AuditLogServiceImpl.java) |

| 对话历史自动过期 | Redis TTL 机制，超期自动清除 | `redis_client.py` `set_chat_history()` |
| HTTPS 传输 | 生产环境强制 HTTPS | 部署配置 |
| API 鉴权分层 | 公开接口白名单（网点/凭证校验/直通码图片/AI 服务）；其余需 Bearer Token | `WebConfig.addInterceptors()` |

## 四、算法可解释性说明

### 4.1 关键决策逻辑透明度

| AI 环节 | 决策逻辑 | 透明度 | 可解释方式 |
|---------|---------|--------|-----------|
| 材料预检 | `BUSINESS_MATERIALS` 配置表定义必填字段 → 逐项检查空值 | **100% 可解释** | `missing`/`required` 字段直接告知缺失项；`missingLabels` 中文标签 |
| 数字人对话（规则层） | 17 条 `KB_RULES` 按优先级正则匹配 → 命中返回固定话术 | **100% 可解释** | `intent` 字段返回匹配的意图标签 |
| 数字人对话（LLM 层） | 通义千问生成 | **部分可解释** | `model_source` 字段标注来源（`rule_kb`/`llm`/`rule_fallback`） |
| 热力图预测 | 历史客流 → 线性回归 → 状态基线融合 → 确定性扰动 | **可解释** | 负载百分比可追溯至历史数据+算法参数 |
| 预填单解析 | 正则提取字段 + 关键词推断业务类型 + 置信度计算 | **100% 可解释** | 返回提取的各字段值 + 置信度 + 推断的业务类型 |
| 健康诊断（规则层） | 画像维度 → 模板化拼接 | **100% 可解释** | 画像数据字段化输出 |
| 健康诊断（LLM 层） | 画像 prompt → 通义千问生成 | **部分可解释** | 画像数据可追溯，但 LLM 生成过程为黑盒 |
| 审计哈希链 | SHA-256(prevHash + 字段拼接) | **100% 可解释** | 逐条 hash 可验证，链完整性可校验 |

### 4.2 可追溯性

**审计哈希链**（[AuditLogServiceImpl.java](file:///d:/MyProject/-/lingmou_backend/src/main/java/com/icbc/lingmou/service/impl/AuditLogServiceImpl.java)）：

```
hash_n = SHA256(prevHash_n-1 + operatorId + operatorName + action + content_n)
```

- 链首 `prevHash` = 64 个 "0"
- 每条记录的 `hash` 依赖前一条的 `hash`，形成链式结构
- `GET /api/audit/my/verify` 逐条重算 hash 并比对，任何篡改都会导致链断裂
- `GET /api/audit/my` 返回逐条 `hashValid` 字段，前端可视化标注每条记录的自洽状态
- 审计 `content` 包含：voucherNum、sn、业务类型、用户身份、办理状态、时间戳等，形成完整操作证据链

**直通码生成全链路可追溯**：

```
预填单创建(POST /api/preforms) → preFormId 落库
  → 直通码生成(POST /api/qrcode/generate) → AI预检 → T码签发 → 审计上链
  → 预约创建(POST /api/appointments) → V凭证号生成 → vouchers关联行
  → 绑定(PUT /api/qrcode/{num}/bindAppointment) → appointment_id 回填
  → 审计查询(GET /api/audit/my) → 链上存证可验证
```

每个环节的输出均可作为下一环节的输入追溯，任何一环失败不影响已签发数据（best-effort 策略，`auditSynced` 字段标注存证状态）。

## 五、AI 伦理风险评估

### 5.1 算法偏见风险

| 风险点 | 具体表现 | 风险等级 | 防控措施 |
|--------|---------|---------|---------|
| 信用分偏置 | 信用分影响预约权限（`CREDIT_TOO_LOW` 11009），若评分逻辑含隐含偏见可能导致歧视 | 中 | 当前信用分基于用户行为（完成/取消/超时），非 demographic 特征；`POST /api/credit/adjust` 仅限管理员操作，有审计留痕 |
| 网点推荐偏向 | 热力图预测可能持续推荐某些网点，导致客流不均衡 | 低 | 预测基于历史客流数据（非用户画像），确定性扰动保证结果分布均匀；用户可自主选择网点 |
| 诊断画像偏差 | 诊断以 userId 为种子确定性合成画像，不同用户画像差异大 | 低 | 画像为演示用合成数据（非真实行为），生产环境应接入真实统计数据；画像数据可追溯（userId→种子→各维度值） |

### 5.2 信息茧房风险

| 风险点 | 具体表现 | 风险等级 | 防控措施 |
|--------|---------|---------|---------|
| 业务推荐窄化 | AI 对话基于 17 条规则匹配，长期可能只推荐熟悉业务 | 低 | 规则覆盖 6 大业务类型，且 LLM 兜底覆盖长尾；用户可自由输入任意问题 |
| 网点推荐固化 | 热力图可能反复推荐同一"畅通"网点 | 低 | 算法含确定性扰动，同一网点不同时段预测值不同；用户可查看全部网点列表自主选择 |
| 诊断建议同质 | LLM 可能对相似画像生成相似诊断 | 低 | 画像 12 维参数随机组合，用户间差异大；`temperature=0.7` 增加输出多样性 |

### 5.3 深度伪造风险

| 风险点 | 具体表现 | 风险等级 | 防控措施 |
|--------|---------|---------|---------|
| AI 冒充人工 | 用户可能误以为 AI 数字人是真人客服 | 中 | AI 回复明确自称"灵枢AI数字人大堂经理"；系统 prompt 要求 AI 以"灵枢 AI"自称 |
| 对话内容伪造 | LLM 可能生成不当建议 | 中 | 规则层话术为预设合规文案（逐字审核）；LLM 层有 system prompt 约束角色边界；金融建议不含具体产品推荐 |
| 凭证伪造 | 伪造直通码骗取服务 | 高 | T 直通码含 CRC16 校验位，`isValidDirectCode` 逐位校验；V 凭证有格式校验；审计链可追溯签发来源 |

### 5.4 责任归属风险

| 风险点 | 具体表现 | 风险等级 | 防控措施 |
|--------|---------|---------|---------|
| AI 建议误导 | AI 诊断建议不当导致用户损失 | 中 | 诊断 prompt 约束为"财富健康度建议"，不涉及具体投资产品；`model_source` 标注来源，用户可知是否为 AI 生成 |
| 预检遗漏 | AI 预检通过但实际材料不全 | 低 | 预检基于确定性规则（非模型），`required` 字段透明展示校验标准；用户可自行核对 |
| 预测不准 | 热力图预测与实际客流偏差 | 低 | 预测为参考性建议，不作为强制分流；用户可实时查看网点状态；算法含扰动避免过度自信 |
| 审计篡改 | 审计链被篡改导致责任无法追溯 | 高 | SHA-256 哈希链防篡改；`verifyChain` 逐条校验；管理员操作有独立审计留痕（operatorId/operatorName） |
| 数据泄露 | 用户 PII 泄露 | 高 | JWT 认证+用户隔离；PII 脱敏；Redis TTL 自动清除对话；LLM 不传输身份证/手机号；WebConfig 公开接口白名单严格管控 |

### 5.5 综合防控措施

1. **规则优先、AI 兜底**：所有涉及金融业务决策的环节（预检、凭证签发、审计上链）均采用确定性规则引擎，LLM 仅用于非决策性内容生成（对话回复、诊断文案），不参与业务审批
2. **全程可追溯**：审计哈希链记录每次直通码签发的完整上下文（凭证号、业务类型、身份信息、时间戳），任何操作可回溯到具体用户和时刻
3. **分层鉴权**：公开接口白名单严格管控；客户侧接口按 userId 强制隔离；管理员接口限 AUDITOR/RISK/ADMIN 角色
4. **降级策略**：LLM 不可用时自动降级为规则兜底（`model_source` 标注），Redis 不可用时对话退单轮、热力图走内存计算，保证核心业务不中断
5. **透明标注**：AI 生成内容标注 `model_source` 来源（`rule_kb`/`llm`/`rule_fallback`），用户可区分规则回复与 LLM 回复
6. **PII 保护**：身份证/手机号在审计响应中脱敏；对话历史 Redis TTL 自动过期；LLM 调用不传输敏感 PII
7. **密钥安全**：LLM API Key 通过环境变量读取（`DASHSCOPE_API_KEY`），不硬编码于源码；JWT Secret 部署时配置

### 5.6 已知局限与改进方向

| 局限 | 当前状态 | 改进方向 |
|------|---------|---------|
| 审计 content PII 明文落库 | 既有 schema 设计，仅在响应层脱敏 | 升级为入库前脱敏或 AES-256 加密存储 |
| 诊断画像为合成数据 | 基于 userId 确定性生成，非真实行为统计 | 接入真实用户行为数据（预约统计、业务偏好） |
| LLM 输出内容审核 | 依赖 system prompt 约束 + 规则优先 | 增加输出内容后置审核（敏感词/合规检查） |
| 对话历史明文存储 | Redis 中 JSON 明文，TTL 过期清除 | 敏感对话内容加密存储 |
| 热力图预测精度 | 基于合成历史数据+线性回归 | 接入真实客流统计，升级为 ARIMA/Prophet 等时序模型 |
| 无模型偏见检测 | 当前规则引擎无 demographic 偏见风险 | LLM 层增加偏见检测与去偏处理 |
