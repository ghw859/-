## 四、接口集成检测

### 4.1 接口规模

- Java 业务后端：**11 个 Controller、49 个 HTTP 端点**，统一响应结构 `{code, msg, data}`，错误码按业务域分段。
- Python AI 服务：**7 个路由端点**（健康检查、数字人对话、WebSocket 多轮对话、AI 诊断、客流热力图、材料预检、预填单解析兜底）。
- 前端经 nginx 统一入口反代：`/api/ai/*` → AI 服务，其余 `/api/*` → Java 后端。

### 4.2 端到端主链路（16 步全通）

以真实账号登录获取 JWT 后逐环走查：登录 → 总览 → 建预约（V 号）→ 凭证校验（APPOINTMENT 类型）→ 二维码取图（200 公开放行）→ 连续推进 4 步至完成 → 终态再推进被拒 → 建预填单 → 材料预检缺料拦截 → 补料后生成 T 码 → T 凭证校验（DIRECT_CODE 类型）→ T 码图片/审计链/链校验通过 → AI 热力图 → AI 数字人 → AI 诊断 → AI 服务宕机降级（后端返回 60001 中文提示，其余接口不受影响）。**16 步全部通过。**

## 五、安全性检测

| 检测项 | 方法与结果 |
|--------|-----------|
| 身份认证 | 口令 BCrypt 散列存储，不明文落库；接口持 JWT 访问；伪造/失效令牌返回 11008 |
| 角色授权（RBAC） | 普通用户访问审计接口 `/audit/logs`、链校验接口被拒（10003）；仅 AUDITOR/RISK 放行 |
| 水平越权防护 | 用户 B 读取、推进用户 A 的预约均被拒（10003）；预约列表、审计链均按本人 ID 过滤，不返回他人数据 |
| 数据隔离 | 审计日志按 operator_id 隔离，用户 B 查询自身审计链为 0 条，不可见用户 A 记录 |
| 防篡改 | 审计记录以 SHA-256 前向指针串联，任意篡改即断链，链校验接口可检出（verify：intact） |
| 凭证自校验 | T 码内含校验位，篡改校验位/长度非法均判定 invalid；直通码重复绑定到他人预约被拒（20009），同号重复绑定幂等 |
| 敏感信息 | 凭证图片查询接口公开放行但不返回任何个人敏感信息（PII），仅返回号码、时间、类型 |
| 密钥管理 | 数据库口令、JWT 密钥、大模型密钥均经环境变量/`.env` 注入，`.env` 已加入 `.gitignore`，不进入代码仓库 |

**说明**：本次安全检测覆盖认证、授权、越权、数据隔离与业务防篡改逻辑；未开展专业渗透测试与漏洞扫描器扫描，建议正式上线前补充。

## 六、性能检测（接口响应时延抽测）

### 6.1 检测方法

2026-09-18 在本地 Docker Desktop 单宿主机环境，对 10 个代表性接口通过 curl 实测：每接口预热 1 次、正式计时 10 次，共 **100 次请求，HTTP 200 成功率 100%**，统计平均、P95、最小、最大响应时间（含网络回环与服务端全链路处理）。

### 6.2 实测数据

| 接口 | 方法 | 平均 | P95 | 最小 | 最大 |
|------|------|------|-----|------|------|
| 用户登录（含 BCrypt 校验） | POST | 76 ms | 79 ms | 73 ms | 79 ms |
| 服务探活 | GET | 11 ms | 14 ms | 8 ms | 14 ms |
| 数据总览 | GET | 11 ms | 14 ms | 7 ms | 14 ms |
| 我的预约列表 | GET | 11 ms | 13 ms | 9 ms | 13 ms |
| 我的审计链 | GET | 10 ms | 13 ms | 8 ms | 13 ms |
| 网点列表 | GET | 20 ms | 35 ms | 14 ms | 35 ms |
| AI 健康检查 | GET | 7 ms | 8 ms | 4 ms | 8 ms |
| AI 客流热力图（确定性算法） | GET | 9 ms | 13 ms | 6 ms | 13 ms |
| AI 数字人对话（规则引擎命中） | POST | 10 ms | 12 ms | 5 ms | 12 ms |
| 二维码图片生成（ZXing） | GET | 28 ms | 39 ms | 21 ms | 39 ms |

### 6.3 结论与局限

- 常规业务查询接口响应时间约 **7–20 ms**；含口令散列的登录约 **76 ms**；二维码实时生成约 **28 ms**，交互流畅。
- 不依赖大模型的确定性 AI 能力（热力图、规则对话）响应在 **10 ms 量级**，验证了"能确定的不调模型"分层架构在时延上的收益。
- **局限**：以上为单用户、无并发竞争下的接口时延抽测，反映单请求处理效率，不等同于高并发吞吐能力；本次未实施多并发压力测试，建议上线前补充负载测试。

## 七、AI 能力检测

### 7.1 三层 AI 架构

| 层级 | 实现方式 | 代表能力 |
|------|----------|----------|
| L1 确定性规则层 | 正则/规则引擎 | 材料预检、预填单解析 |
| L2 预测算法层 | scikit-learn 时序建模 | 客流热力图预测 |
| L3 大模型理解层 | 统一 LLMClient 接入，模型可插拔 | 数字人多轮对话、个性化诊断 |

### 7.2 检测结果

- **大模型理解能力**：检测期内（2026-09-13）真实调用验证，数字人正确识别"网点推荐"意图（intent=branch_recommend）并生成约 190 字自然语言回复；AI 诊断结合用户画像生成约 336 字个性化建议。
- **确定性 AI 能力**：客流热力图按网点 × 时段输出客流等级与推荐文案，结果可复现；材料预检对缺料场景返回 passed=false 及中文缺失材料清单。
- **成本与合规约束**：预填单解析全程纯正则，不调用大模型，毫秒级返回、零 token 成本、输出完全可控。
- **服务韧性（容错降级）**：大模型密钥未配置或失效时，数字人与诊断自动切换规则引擎，页面不中断；AI 服务整体不可用时，Java 后端返回 60001 中文可重试提示，预约、网点等其余功能正常运行。
- 检测日（2026-09-18）大模型密钥因参赛账号欠费处于停用状态，系统按上述机制平稳运行于规则降级模式；该状态不影响软件已具备的大模型接入能力，充值并配置有效密钥后即恢复 L3 层能力，无需改码。
